# Benchmark 004 — v0.2 (TinyStories), absolute measurement

> **Not a delta vs `001_baseline.md`.** v0.2 changes TWO variables at once relative to v0.1
> — model size (818K→2.75M params) AND dataset (Shakespeare→TinyStories). Per
> [`docs/14`](../docs/14_BENCHMARKING.md)'s one-variable-at-a-time rule, that means this is
> **not** a valid "faster/slower" comparison to 001 — it is reported here as its own
> absolute measurement, for its own record.

## 1. What & why

The first successful v0.2 training run: a ~2.7M-param model trained on TinyStories (the
project's *primary* corpus per [`docs/17`](../docs/17_DATASET_GUIDE.md)), to compare
against v0.1's Shakespeare *sanity* run.

## 2. Machine state

- MacBook Air M1 · macOS 26.5.2 (arm64) · torch 2.13.0 · Device: **mps** · dtype: fp32
- **Thermal/system state during training: NOT clean.** The machine was under real memory
  pressure for reasons independent of this process (swap reached ~94% used, load average
  peaked above 12, physical free memory dropped to double digits of MB at points) —
  confirmed via `ps`/`top`/`vm.swapusage` that the training process itself used only
  ~60 MB RSS, so the pressure was from other concurrent load, not this run. Training took
  **957.6 minutes (~16.0 hours)** for 3375 optimizer steps — far slower than a clean-machine
  run would be expected to take, and this record does not claim otherwise. Treat the
  wall-clock time as machine-specific, not representative.

## 3. Configuration

- Model: L=6, h=6, C=192, block=256, vocab=138 → **2,745,216 params** (matches
  `SPEC.md` §5 and `ADR-0005`'s worked arithmetic exactly)
- Training: batch_size=16, **grad_accum_steps=4** (effective batch 64), lr=5e-4,
  warmup_steps=100, max_steps=3375 → 55,296,000 tokens (Chinchilla ~20:1 budget for this
  param count, per `research/paper_notes/chinchilla.md`)
- batch_size was lowered from an initial 64 to 16 (with grad_accum added to compensate)
  after a real batch=64 run visibly strained the machine — attention activation memory
  scales with `batch_size × block_size²`, and block_size=256 (2× v0.1's 128) made batch
  size the lever to pull. See `configs/train_tinystories.yaml`'s comment for the exact
  token-budget arithmetic preserved by this change.
- Data: TinyStories, 414.7M train / 46.6M val tokens (`datasets/SOURCES.md`), `uint16`
  on-disk via the standard `get_batch` in-memory path (not the new mmap loader — that's a
  separate, already-landed optimization; this run predates wiring it into `train.py`).

## 5. Interpretation

- **Real learning, real quality jump.** Val loss fell from `ln(138)≈4.93` (random init) to
  **0.86** — perplexity ≈2.4, meaning the model is, on average, choosing among roughly 2–3
  plausible next characters rather than blindly guessing among 138. The generated sample
  (`outputs/trained_tinystories_v0_2_sample.txt`) is qualitatively more fluent than v0.1's
  Shakespeare sample — real names, coherent short sentences, dialogue punctuation used
  correctly — consistent with `docs/17`'s thesis that TinyStories is the better capacity
  match for a model this size.
- **v0.2 is markedly slower per-token than v0.1** (21K vs 65K train tok/s; 28 vs ~83–137
  gen tok/s) — expected: 3.4× the parameters, 2× the block_size (attention cost scales
  with block_size²), and this specific run measured under real system memory pressure
  unrelated to the model itself. Not a regression to chase; a different, larger model.
- **Memory still fits comfortably**: 1.6 GB architecture footprint vs 8 GB total, before
  even accounting for the mmap loader's separate RAM win on the corpus side.
- **Not a valid speed comparison to v0.1** — restated from the top: two variables changed
  at once. A real v0.1-vs-v0.2 speed delta would require holding the dataset fixed.

## 6. A real bug found and fixed while banking this milestone

`scripts/generate.py` failed hard on this checkpoint: it built a throwaway model
hardcoded to v0.1's exact shape (`n_layer=4, n_embd=128, block_size=128, vocab_size=65`)
just to read the checkpoint's stored config, but `load_checkpoint()` always calls
`model.load_state_dict(strict=True)` internally — so the "peek" only ever worked by
coincidence when the target checkpoint happened to already be v0.1-shaped. Fixed by
reading the config via a raw `torch.load(...)['config']` first, with no model required for
that step, then constructing the correctly-shaped model once. A regression test
(`tests/test_generate_script_smoke.py`) now runs the real script against a deliberately
non-v0.1-shaped checkpoint, closing a gap where **no test had ever executed
`generate.py`** end-to-end before this.

## 7. Reproduce

```bash
python scripts/train.py --config configs/train_tinystories.yaml --data_dir datasets/tinystories
python scripts/generate.py --checkpoint checkpoints/best_model.pt \
    --meta datasets/tinystories/meta.json --prompt "Once upon a time" \
    --temperature 0.8 --top_k 40 --max_new_tokens 500
python scripts/benchmark.py --config configs/train_tinystories.yaml --gen_tokens 200
```
